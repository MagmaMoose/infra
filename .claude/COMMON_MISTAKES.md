# Common Mistakes & Gotchas

1. **`backend.tf`/`provider.tf`** — auto-generated by terragrunt (`if_exists=overwrite`). Edit `terraform/root.hcl`.
2. **SOPS first** — wrong order. Use OCI Vault → 1Password → SOPS (last resort, `.enc.yaml` only).
3. **New CNPG `Cluster`** — one shared `postgres` exists in `database` ns. Add `Database`+`User` CRs to it.
4. **Over-allocating Pi pods** — ~4-8GB usable. Default `t.small`; `c.medium` only for real multi-core.
5. **`git push` ≠ deployed** — Flux reconciles on intervals. Force: `flux reconcile kustomization <name> -n flux-system`.
6. **Atlantis autoplan misses shared changes** — `when_modified` only sees each leaf's subtree. Edits to `root.hcl`, `region.hcl`, `modules/**` need manual `atlantis plan -p <project>` per affected leaf.
7. **Plaintext secrets** — PUBLIC repo. Rotate immediately if leaked.
8. **AI co-author trailers** — commit hook rejects `Co-Authored-By:`. Omit.
9. **Parallel agents** — k8s + tf share one checkout; use a worktree for tf to avoid git-op collisions.
10. **Ansible without `--check`** — dry-run real-host playbooks first.
11. **Pre-commit** — `calebsargeant/pre-commit-hooks` must pass before commit.
12. **Restarting `hermes` (amd64-only, RWO Longhorn) can strand it** — it's pinned to the single on-prem amd64 worker `ff-vm1`, which is CPU-*request*-saturated (~63% real use but requests fully reserved). With `strategy: Recreate` a restart deletes the pod first, and queued pods grab its freed CPU, so the new pod stays `Pending` (FailedScheduling: Insufficient cpu). Right-size the CPU *request* (it has no CPU limit, so it still bursts). Same trap for any amd64-pinned app on ff-vm1. When patching a Flux-managed value live, `flux suspend kustomization <name>` first or Flux reverts it in ≤10m.
13. **Replacing a `resource-profiles` component — copy the LIMIT, not just the request.** A profile sets requests *and* limits (`m.nano` = req 150m/768Mi, **lim 500m/2Gi**). When inlining measured values, it is easy to carry the profile's *request* figure into the limit line. `litellm` shipped `limits.memory: 768Mi` against a real working set of **1134Mi**, so every new pod was `OOMKilled` (exit 137) — and it produced **no logs at all**, because it died before writing any; only `lastState.terminated` named the cause. It stayed serving purely because the old ReplicaSet was still up. Check `bazarr`-style cases too: a limit within ~10% of measured use is a deferred OOM, not a right-sizing. Measure with `kubectl exec <pod> -- cat /sys/fs/cgroup/memory.current` when the Metrics API is down.
14. **`request == limit` is only safe above true peak.** The Guaranteed-QoS rule turns a *measured average* into a hard cap. On a node at 99% memory requested you often cannot raise the request — but **limits are not scheduler-reserved**, so raising the limit alone is free and is the correct fix. Keep the request honest for scheduling; give the limit headroom for spikes.
15. **A rollout can deadlock on a full node.** `maxUnavailable: 25%` of 2 replicas rounds to **0**, so the controller will not free the old pod until the new one is Ready — while the new pod cannot schedule until that memory is freed (`FailedScheduling: Insufficient memory`). The Deployment still reports `ready=2`, so it looks healthy. Break it with `kubectl scale rs <old-rs> --replicas=0`, not by deleting the pod (its RS just recreates it).
16. **`node-role.kubernetes.io/*` node labels cannot be made durable via k3s `node-label:`.** The kubelet is forbidden from self-registering them, so they must be applied out-of-band and are **lost if the Node object is recreated** (they do survive reboots). Anything pinned to `node-role.kubernetes.io/system` — which includes the Flux controllers — becomes unschedulable if that happens. Prefer a custom prefix such as `topology.sargeant.co/*`, which the kubelet *can* self-register.
17. **A kustomize `patches:` target that matches nothing fails SILENTLY.** Changing a workload's kind (DaemonSet → StatefulSet) orphans every patch whose `target.kind` still names the old one, and `kustomize build` neither warns nor errors — it just renders the unpatched manifest. Converting `timemachine` did exactly this: the resource patch stopped applying, so the memory *request* jumped from the patched `256Mi` to the `1157Mi` inline in the file, on a node already at ~99% memory requested. It would have presented as a pod stuck `Pending` with nothing in the diff to explain it. After any kind/name change, re-render and diff the resources against the previous kind, don't just check that it builds.
18. **A chart's `nodeSelector` key is only real if you RENDER it.** The placement-label traps (#13, #17, and the `placement.sargeant.co` HelmRelease guard) all have a sibling inside chart *values*, and it has now shipped three times: (a) **`global.nodeSelector` loses to a non-empty per-component default.** kyverno 3.8.2 sets `global.nodeSelector: {}` but gives every controller `nodeSelector: {kubernetes.io/os: linux}`, and the chart's own comment says "non-global values will override the global value" — so the repo's `global.nodeSelector: node-role.kubernetes.io/system` was inert for its entire life and kyverno sat on ff-pi1 by scheduler accident. Set it per component and carry the `kubernetes.io/os: linux` default forward, since replacing the map replaces it wholesale. (b) **A pod-level field set per container is discarded.** 1Password Connect renders `connect-api` and `connect-sync` as two containers in ONE pod, so `connect.api.nodeSelector`/`connect.sync.nodeSelector` are keys the chart does not have; the Deployment rendered with no nodeSelector at all while the sibling `operator.nodeSelector` — correct — visibly worked. The tell in both cases is the same and takes one command: `kubectl get deploy X -o jsonpath='{.spec.template.spec.nodeSelector}'` returning empty or the bare chart default. Verify with `helm template ... -f <the HelmRelease's values>` and diff the rendered pod spec; never conclude a pin works because the values file reads as though it should. Both defects presented identically to *no* pin — which is invisible until the target node is the one that falls over.
19. **The Pi 5 runs a 16KB page size, and jemalloc-linked images cannot start on it.** ff-pi1 boots `kernel_2712.img`, whose page size is **16384**, not 4096. Anything bundling a jemalloc built for 4KB pages aborts at startup with `<jemalloc>: Unsupported system page size` followed by `errno=12 Cannot allocate memory` — every allocation fails, so the process exits 1 immediately and crash-loops forever. `fluent-bit` did exactly this **147 times** while the other three nodes (amd64 ff-vm1, arm64 OCI VMs — all 4KB pages) ran the identical DaemonSet at 0 restarts, which is the tell: *one node failing while its identical peers are fine, on a Pi, means check `getconf PAGESIZE` before anything else.* **Do not attempt to upgrade out of it** — 3.2.2, 4.2.8 and 5.1.0 were each run on the node and failed identically. The fix is `kernel=kernel8.img` in `/boot/firmware/config.txt` (the stock ARM64 4KB kernel, same firmware package) plus a reboot; see `ansible/firefly-pi-page-size.yaml`, which backs up config.txt and asserts the surviving entries first because the firmware has **no** fallback and a bad config.txt means physically retrieving the machine. Go binaries (Grafana Alloy) are unaffected — no jemalloc. Bonus: 16KB pages round every small allocation up to 16KB, so switching to 4KB gives measurable RAM back on a memory-bound node.
20. **A `patches:` target named by NAME breaks when the *other* repo renames the workload — and nothing in either repo can see it.** Sibling of #17 (which is the *kind* variant): `kubernetes/apps/nievah/prod/flux-kustomization.yaml` overrides `REDIS_URL` to `valkey-oci` for the two OCI-tier nievah Deployments, because a cloud-tier pod must not reach back across the VPN for every cache op. One target said `name: nievah` — the **container** name; the Deployment is `nievah-backend`. When `MagmaMoose/nievah#113` renamed `Deployment/nievah` → `Deployment/nievah-backend`, the patch matched nothing and silently stopped applying, so the **ingest** fell back to the on-prem `valkey` while the **worker** stayed on `valkey-oci`. Both pods were `Running` and `Ready`, Flux was `True`/`Applied revision:`, no error appeared anywhere: the API just enqueued `review_pr`/`triage_pr` jobs into a queue no worker polled. **Every PR review and triage across the whole fleet silently stopped for 7 hours** while 27 jobs piled up in `nievah:arq:queue` on the wrong instance — and the worker's own health line read `queued=0`, because it was truthfully reporting the queue it *could* see. The tell for any split-brain-by-config: compare the two halves directly rather than reading either one's status — `kubectl get deploy -n <ns> -o json | jq '.items[]|{d:.metadata.name,env:...}'`, then `zcard` the queue from *both* pods. A queue that is non-empty from one pod and empty from the other is not a race, it is two different databases. Guard: `target.name` is the **Deployment** name and `containers[].name` is the container name — they differ often; a cross-repo rename has no CI that links them, so re-check `kubectl get deploy` after any app-repo rename.
21. **Two clusters share `apps/` + `components/`** — `kubernetes/apps/` is firefly's set EXCEPT `access-control` (franklinhouse-only). Adding it to `kubernetes/apps/kustomization.yaml`, or pointing franklinhouse at `../../apps`, cross-deploys a whole cluster's workloads. Build **both** roots after touching either shared tree.
22. **`kustomize build` on a `flux-system/` dir fails** — both clusters' bootstrap dirs reference `../apps.yaml`, which trips kustomize's path restriction. Not a bug: add `--load-restrictor LoadRestrictionsNone` (Flux does not enforce it).
23. **franklinhouse Postgres is node-pinned with no backups** — `storageClass: local-path` binds each PVC to one node and there is no `.spec.backup`. Losing a Proxmox host makes those volumes unreachable. See `docs/reference/franklinhouse.md`.
24. **The two clusters do not share a placement vocabulary — a nodeSelector copied across is a guaranteed outage.** firefly labels nodes `topology.sargeant.co/tier` + `node-role.kubernetes.io/*` (servers untainted); franklinhouse uses a bare `node-role` key and taints its system nodes `node-role.kubernetes.io/control-plane=true:NoSchedule`. **Neither key exists on the other cluster.** When #629 split ARC into a cluster-neutral base + per-cluster overlays, franklinhouse's overlay was written with firefly's `topology.sargeant.co/tier: native-cloud` and comments describing an `fh-oci1`/`fh-oci2` pair that **does not exist in this repo or in terraform** — franklinhouse is six amd64 Proxmox VMs. The failure does not look like placement: the Deployment applies cleanly, only the *pod* is refused, so with `wait: true` it surfaces 10 minutes later as `Helm install failed ... context deadline exceeded`, then `Stalled/RetriesExceeded` after four retries, and everything downstream reports the unrelated-sounding `dependency 'arc-systems/arc' is not ready`. The controller sat `Pending` 4h33m. Sibling of #16/#18, but the trigger is *sharing a base between clusters* rather than a chart's values. Two rules: (a) the ONLY check is `kubectl get nodes --show-labels` **on the target cluster** — never infer a label from the sibling overlay that "already works"; (b) on franklinhouse, selector and toleration must travel **together**, since selecting a tainted system node without the toleration reproduces the identical Pending pod. `components/node-selectors/franklinhouse-system` pairs them, but it patches `kind: Deployment` and **cannot reach a Helm-rendered pod spec** — for a HelmRelease, set both in `spec.values`.
25. **An ARC scale set pointed at absent capacity swallows other repos' CI instead of failing.** Every scale set in both clusters advertises `pool-self-hosted`, the org-wide arch-agnostic pool. A listener acquires jobs from that pool the moment it starts and acquires them **whether or not it can schedule a runner pod** — so a scale set whose nodes are missing, unlabelled or full does not error; it accepts work and holds it, and the job shows `queued`/`runner_id: 0` with nothing wrong on the GitHub side. Blast radius is every private repo in the org, and the tell is only visible cluster-side (`kubectl get pods -n arc-runners` showing `Pending` runners). This inverts the usual triage instinct: when #629's franklinhouse controller was broken, that was the *safe* state — nothing could register. **Fixing a broken ARC controller without first checking that every scale set it will bring up has schedulable capacity makes the outage worse and quieter.** Gate the scale set out of the overlay until the capacity is real, and record the precondition plus the command that proves it. Note a runner needs its *summed* pod requests (the franklinhouse runner is 350m/960Mi across all containers, not the 50m/64Mi any single one shows), so a merely `Ready` node is not evidence — `kubectl describe node <n> | grep -A8 'Allocated resources'` is.
26. **Naming a private workload in a public artifact cannot be taken back.** This repo is public and some of what runs on these clusters is not — the `internal` namespace and a couple of sibling repos are private by convention, not by any technical control, so nothing stops you pasting a name into a commit message or PR body. A troubleshooting write-up is the easy way to do it: naming the pods a change happened to evict reads as diligence and is exactly the leak. It landed in a squash-merged commit within the hour, and while the file was fixed forward in the next PR, **the string stays in main's history and in the PR's diff view permanently** — force-pushing a public branch does not retract it either, since GitHub keeps orphaned commits reachable by SHA. Cost of prevention is one word: say "lower-priority pods", "other workloads on the node", "a replicated datastore" and the write-up loses nothing. Before pushing anything with prose in it — commit message, PR body, code comment, ADR — grep the whole surface, not just the diff: `git log origin/main..HEAD --format=%B` and the rendered PR body both carry text that `git diff` does not show.
