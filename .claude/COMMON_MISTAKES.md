# Common Mistakes & Gotchas

1. **`backend.tf`/`provider.tf`** — auto-generated by terragrunt (`if_exists=overwrite`). Edit `terraform/root.hcl`.
2. **SOPS first** — wrong order. Use OCI Vault → 1Password → SOPS (last resort, `.enc.yaml` only).
3. **New CNPG `Cluster`** — one shared `postgres` exists in `database` ns. Add `Database`+`User` CRs to it.
4. **Over-allocating Pi pods** — ~4-8GB usable. Default `t.small`; `c.medium` only for real multi-core.
5. **`git push` ≠ deployed** — Flux reconciles on intervals. Force: `flux reconcile kustomization <name> -n flux-system`.
6. **Atlantis autoplan misses shared changes** — `when_modified` only sees each leaf's subtree. Edits to `root.hcl`, `region.hcl`, `modules/**` need manual `atlantis plan -p <project>` per affected leaf.
7. **Plaintext secrets** — PUBLIC repo. Rotate immediately if leaked.
8. **AI co-author trailers** — commit hook rejects `Co-Authored-By:`. Omit.
9. **Parallel agents** — k8s + tf share one checkout; use a worktree for tf to avoid git-op collisions.
10. **Ansible without `--check`** — dry-run real-host playbooks first.
11. **Pre-commit** — `calebsargeant/pre-commit-hooks` must pass before commit.
12. **Restarting `hermes` (amd64-only, RWO Longhorn) can strand it** — it's pinned to the single on-prem amd64 worker `ff-vm1`, which is CPU-*request*-saturated (~63% real use but requests fully reserved). With `strategy: Recreate` a restart deletes the pod first, and queued pods grab its freed CPU, so the new pod stays `Pending` (FailedScheduling: Insufficient cpu). Right-size the CPU *request* (it has no CPU limit, so it still bursts). Same trap for any amd64-pinned app on ff-vm1. When patching a Flux-managed value live, `flux suspend kustomization <name>` first or Flux reverts it in ≤10m.
13. **Replacing a `resource-profiles` component — copy the LIMIT, not just the request.** A profile sets requests *and* limits (`m.nano` = req 150m/768Mi, **lim 500m/2Gi**). When inlining measured values, it is easy to carry the profile's *request* figure into the limit line. `litellm` shipped `limits.memory: 768Mi` against a real working set of **1134Mi**, so every new pod was `OOMKilled` (exit 137) — and it produced **no logs at all**, because it died before writing any; only `lastState.terminated` named the cause. It stayed serving purely because the old ReplicaSet was still up. Check `bazarr`-style cases too: a limit within ~10% of measured use is a deferred OOM, not a right-sizing. Measure with `kubectl exec <pod> -- cat /sys/fs/cgroup/memory.current` when the Metrics API is down.
14. **`request == limit` is only safe above true peak.** The Guaranteed-QoS rule turns a *measured average* into a hard cap. On a node at 99% memory requested you often cannot raise the request — but **limits are not scheduler-reserved**, so raising the limit alone is free and is the correct fix. Keep the request honest for scheduling; give the limit headroom for spikes.
15. **A rollout can deadlock on a full node.** `maxUnavailable: 25%` of 2 replicas rounds to **0**, so the controller will not free the old pod until the new one is Ready — while the new pod cannot schedule until that memory is freed (`FailedScheduling: Insufficient memory`). The Deployment still reports `ready=2`, so it looks healthy. Break it with `kubectl scale rs <old-rs> --replicas=0`, not by deleting the pod (its RS just recreates it).
16. **`node-role.kubernetes.io/*` node labels cannot be made durable via k3s `node-label:`.** The kubelet is forbidden from self-registering them, so they must be applied out-of-band and are **lost if the Node object is recreated** (they do survive reboots). Anything pinned to `node-role.kubernetes.io/system` — which includes the Flux controllers — becomes unschedulable if that happens. Prefer a custom prefix such as `topology.sargeant.co/*`, which the kubelet *can* self-register.
